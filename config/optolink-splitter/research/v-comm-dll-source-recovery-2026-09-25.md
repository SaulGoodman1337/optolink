# V-Comm DLL source recovery — 2026-09-25

Status: **completed static extraction / no execution of installer**

## Purpose

The historical OpenV archive `files/v_comm_dll.zip` was revisited because
public forum posts from 2010/2013 referred to modifications of `v_comm_dll`
for later Viessmann controller families. The surviving ZIP appeared, at first,
to contain only a Wise installer and documentation.

For the WB2A firmware-over-Optolink work, the relevant question was:

> Does the original V-Comm implementation contain a raw/service/monitor read
> path beyond ordinary P300 Virtual_READ/Virtual_WRITE?

The installer was therefore unpacked statically.

## Exact 20C2 / VDensHO1 support is present

The recovered VB6 class contains:

```text
Public Enum V_Type
    VDensHO1 = &H20C2
    V333MW1  = &H20B8
    V100GC1  = &H20A0
    V200GW1  = &H20A4
End Enum
```

Therefore this is not merely a generic Optolink library: the original source
contains explicit support for the exact local device identity:

```text
VDensHO1 / 20C2
```

The class also contains a dedicated `Vito_Data_VDensHO1` address table, with
examples including:

```text
0x5525 outside temperature
0x0810 boiler temperature
0x555A boiler target
0x7660 internal pump
0xA38F burner/power state
0x7507 error history
0x00F8 device identity entry point
```

These independently match the P300/VDensHO1 object model used by the current
project.

## Serial and protocol initialization

The class configures:

```text
4800 baud
even parity
8 data bits
2 stop bits
```

Protocol entry is:

```text
16 00 00
```

and a successful start is recognized by response `0x06`.

A `0x04` byte is used for protocol termination/recovery.

This is the familiar VS2/P300 activation path.

## Exhaustive serial-output audit

Every assignment to `SerialPort.Output` in `v_comm.cls` was enumerated.

The only transmit paths are:

```text
0x04                        protocol stop
0x16 0x00 0x00              protocol start

V_DLL_Format_Query(...)     read request
V_DLL_Get_Write_String(...) write request
```

There is no separate public or private raw-send routine, monitor command,
boot/ROM service, arbitrary function-code API, high-address request, page
selector or bank selector in this class.

### Read request formatter

`V_DLL_Format_Query(Requested, reply_data_len)` computes only:

```text
byte1 = high byte of 16-bit requested address
byte2 = low byte of 16-bit requested address
```

and emits the LDAP/P300 payload:

```text
00 01 <addr_hi> <addr_lo> <len>
```

wrapped in the normal VS2 frame:

```text
41 05 00 01 <addr_hi> <addr_lo> <len> <checksum>
```

Function code is hard-coded:

```text
0x01 = Virtual_READ
```

The address parameter is a VB6 `Integer`, and the serializer contains no
third address byte.

### Write request formatter

`V_DLL_Get_Write_String()` similarly hard-codes:

```text
0x02 = Virtual_WRITE
```

with only the same two address bytes.

No other P300 function code is generated by the source.

## Firmware-read conclusion

This is unusually strong negative evidence because the recovered source:

1. explicitly supports **VDensHO1 / 20C2**;
2. exposes the full transport implementation;
3. has an exhaustively enumerable set of serial writes;
4. contains no hidden generic/raw function-code interface.

Therefore the original public V-Comm DLL is **not** the missing WB2A
program-ROM reader.

It cannot directly address the assumed M30624 program-flash range:

```text
0xC0000..0xFFFFF
```

because its target address is serialized as only 16 bits.

## Relation to the historical M30612 readout claim

This result makes an important separation clearer:

```text
public V-Comm / VDensHO1 20C2 client
    -> ordinary P300 Virtual_READ/Virtual_WRITE
    -> not firmware acquisition

historical V200KW2 / M30612MC statement
    -> "SW lässt sich mit etwas Aufwand über Optolink auslesen"
    -> exact mechanism still unrecovered
```

The M30612 claim therefore should not be explained away as ordinary V-Comm
bulk reading. Its special mechanism remains a distinct archival/reverse-
engineering target.

## Effect on the Walter/wkiffe VScotHO1 lead

Public forum posts state that Walter/wkiffe modified `v_comm_dll` for
`VScotHO1`.

The recovered base source shows what such a modification most naturally
looked like: adding/changing device IDs, address maps or read/write handling
on top of the existing P300 transport.

Unless Walter also added a new raw/service API, that branch is now less likely
to contain the old M30612 firmware dump mechanism.

It is still worth recovering because it may document later controller-family
differences, but it is no longer the primary firmware-acquisition lead.

## Reproducibility boundary

No third-party binaries/source are copied into this repository by this note.

The evidence can be reproduced from the public OpenV wiki archive:

```text

  -> setup_vcomm.exe

```

The hashes above identify the exact files inspected.

## Research decision

Close the following hypothesis:

> The surviving public V-Comm DLL contains a hidden VDensHO1 firmware/program-
> ROM read path.

It does not.

Keep open:

1. the **M30612-era special Optolink readout mechanism** documented by KarlKoch;
2. a controller-side **RPC/monitor/page service** not exposed by base V-Comm;
3. an older GWG/KW-specific service path absent from the P300-only V-Comm
   implementation;
4. another historical utility/source from the lost OpenV developer material.

The current highest-value archival target remains the actual material behind
KarlKoch's M30612 disassembly, not the base V-Comm package.
