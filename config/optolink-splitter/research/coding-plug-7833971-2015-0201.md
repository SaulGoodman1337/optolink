## Identity

```text

0x7656 = 20150201       -> 2015:0201
```

This document contains only findings associated with the coding-plug/GWG parameter layer, not general live controller behavior.

## Burner characteristic GWG91-GWG9A

Vitosoft identifies these coding-plug values as modulation degree at 10..100 % burner output.

Measured:

```text
0x1090 = 00 21 21 21 2f 37 3f 48 51 5a 64 00 00 00 00 00
```

Decoded characteristic:

| Burner output | Modulation value |
| ---: | ---: |
| 10 % | 33 |
| 20 % | 33 |
| 30 % | 33 |
| 40 % | 47 |
| 50 % | 55 |
| 60 % | 63 |
| 70 % | 72 |
| 80 % | 81 |
| 90 % | 90 |
| 100 % | 100 |

This is a key result, but two percentages must be kept separate:

- `0x55DC` and scaled `0xA305` are now hardware-verified as the live
  **Modulationsgrad in percent**. During startup both read about 65-66 %.
- GWG91-GWG9A describe the coding-plug characteristic
  **"Modulationsgrad bei 10..100 % Leistung"**. They are therefore a mapping
  between a power-axis and the modulation-degree axis, not a second live
  modulation signal.
- the practical modulation-degree floor in this characteristic is 33 %;
- a live modulation degree of 65-66 % lies between the characteristic points
  63 @ 60 % Leistung and 72 @ 70 % Leistung.

A simple interpolation of the table would place MOD=65-66 at roughly
62-63 % on the table's `Leistung` axis. That mathematical mapping is useful,
but the exact relationship of the Vitosoft `Leistung` axis to delivered
thermal kW on this exact WB2A has not yet been independently verified.

An earlier working hypothesis that live 65/66 represented 100 % output was
wrong and has been discarded.

## Relation to the newly verified KMBUS read paths

On 2026-09-22 the local VDensHO1 / 20C2 accepted dedicated VS2/P300
KMBUS function codes through the generic Optolink request path.

Measured:

~~~text
KMBUS_RAM_READ    0x41, F8/8 -> 20c2000300000103
KMBUS_EEPROM_READ 0x43, F8/8 -> 5497549754975497
~~~

Both returned retcode 1.

This creates a new research path for the coding plug, but the important
boundary is:

> **KMBUS_EEPROM_READ is not yet proven to read the physical
> Kesselcodierstecker.**

The function name specifically points to a KM-BUS-related EEPROM address
space. The boiler coding plug may instead be connected to a separate internal
interface and merely copied into controller/GWG objects during initialization.

Evidence for treating these as separate until proven otherwise:

- the coding-plug identity and parameter blocks are exposed as structured
  P300 objects such as 0x1010 and 0x1030..0x1090;
- the boiler supports an explicit service workflow to re-read the coding plug
  (coding address 8A:176 followed by 7C:26), which implies a distinct
  controller-side import operation;
- 0x43 at F8..FF does not return the known coding-plug identity or the normal
  controller identity;
- the 0x43 block behaves differently from ordinary linear reads and therefore
  must not yet be interpreted as a raw EEPROM dump.

### What would prove that 0x43 reaches the coding plug

Useful read-only evidence would be one of:

1. locate a real Vitosoft datapoint for this VDensHO1/20C2 whose FCRead is
   KMBUS_EEPROM_READ and whose semantic value is already known from the coding
   plug;
2. find an address range where 0x43 reproduces bytes from known coding-plug
   fields such as the 7833971 identity or GWG60..GWG9A values;
3. compare 0x43 snapshots before and after a documented coding-plug re-read and
   observe deterministic changes tied to the plug;
4. correlate a physical dump of the plug with values returned through 0x43.

Until one of those succeeds, call 0x43 a **KMBUS EEPROM access path**, not a
coding-plug dump.

### Can the coding plug be modified through Optolink?

Not established.

The VS2 function-code lists contain KMBUS_EEPROM_READ, but no verified
KMBUS_EEPROM_WRITE workflow has been demonstrated on this controller. More
importantly, even a generic EEPROM write function would not prove that the
destination is the coding plug.

Some Viessmann coding-plug generations are described publicly as ROM devices,
while other community material refers to physically dumping an EEPROM from an
uninstalled plug. That evidence is from other plug/controller generations and
must not be transferred to part 7833971 without identifying the actual device
technology.

For **7833971 / 2015:0201**, the physical memory type, package and pinout remain
open.

### Physical dump remains an independent path

A read-only dump analyzer is now available:

`tools/analyze-wb2a-coding-plug-dumps.py`

Use it only on raw files already produced by an external programmer. It:

- computes SHA256 for every dump;
- checks multiple reads for byte-for-byte identity;
- reports exact byte/bit differences;
- searches for the locally known identity sequence `20 15 02 01`;
- searches cautiously for ASCII/BCD-like representations of part number
  `7833971` without assuming any one storage format;
- writes a machine-readable JSON report for later correlation.

Recommended first physical workflow:

1. photograph both sides of a **spare** plug before connecting anything;
2. identify the memory IC and programmer model;
3. verify voltage, pinout and memory family from the datasheet;
4. make at least two independent read-only dumps without any erase/write;
5. compare them with the analyzer and require identical SHA256 before treating
   a dump as trustworthy;
6. preserve the original dumps unchanged;
7. only then correlate offsets with the known Optolink `0x10x0` structures.

The highest-value physical next step is still read-only:

- inspect/photograph both sides of a spare 7833971 plug;
- identify every semiconductor marking;
- determine whether the memory is mask ROM, OTP/EPROM, serial EEPROM or another
  device;
- find its datasheet and voltage/interface;
- make two independent dumps and compare hashes before any modification;
- correlate the dump against 0x1010 and 0x1030..0x1090.

If the device is ROM/OTP, modification would require replacing/emulating the
memory rather than rewriting the original part.

## Safety / scope

The current coding-plug work is read-only.

The coding plug carries burner/controller-specific limits and parameters. Unknown values must not be treated as safe write targets merely because they can be read over Optolink.


## Structured-object addressing

A read-only probe on 2026-09-22 showed:

```text
read;0x1030;16 -> valid block
read;0x1038;1  -> retcode 3 / payload 01
```

Therefore the `0x10x0` coding-plug areas are structured P300 objects, not a
flat set of independently addressable member bytes. Notation such as
"GWG73 at byte offset 3 of the 0x1070 object" is preferable to claiming that
`0x1073` is itself a readable P300 address unless separately verified.

This does not invalidate the observed byte-field correlations inside the
returned structures; it only changes how those fields are addressed.

## Historical GWG73 hypothesis

> **Superseded:** an early hypothesis considered a 0.5 s/LSB scale because
> raw 24 would then equal 12 s. The VDensHO1 catalog later established a
> `mult10` seconds conversion, giving **240 s**. The 12-second mapping below
> is retained only as research history.

The `0x1070` object contains raw byte `0x18 = 24` at the field correlated
with Vitosoft's `GWG73: Anfahroptimierung modulierender Brenner`.

The measured regulation hold after normal flame establishment is about 12.1 s.
A hypothetical scale of 0.5 s/LSB would map raw 24 to 12 s, which is numerically
striking. However, no source found so far proves that GWG73 uses 0.5 s/LSB on
this controller generation. Treat this only as a testable correlation, not a
decoded unit.

Viessmann documentation for other controller generations distinguishes:
- actuator travel time of the modulating burner,
- startup-optimization duration,
- regulation delay from ignition to control start,
- burner-start delay.

Those semantics support the existence of separate timing constants, but their
storage/scaling on this WB2A coding-plug format is still unresolved.


## Update after CFDM correlation

A later single-session run compared the live modulation command at `0x55DC`
with the CFDM power-state object at `0xA38F`.

Result:

- `0x55DC` already performs the approximately 1 %/s downward ramp.
- `0xA38F` becomes active after flame establishment and follows that command
  very closely.
- Therefore the observed ramp is generated before the downstream active-power
  state and is not well explained by a generic slow physical actuator alone.

This weakens the earlier hypothesis that an unresolved raw value of 100 in the
coding-plug data represented a 100-second burner-actuator travel time causing
the measured ramp.

`GWG73 = 24 / Anfahroptimierung modulierender Brenner` remains a much more
relevant coding-plug candidate for startup behavior. Its exact unit/scaling is
still unproven; the numerical 24 -> ~12 s relation would require 0.5 s/LSB and
must remain explicitly hypothetical until independently verified.


## Refined VDensHO1 scaling from esphome_vitohome catalog

A separately maintained VDensHO1 catalog in
`SoulSolistice/esphome_vitohome` provides byte offsets, converters and units
for the same GWG coding-plug fields. This resolves several previously unknown
scales.

For the measured WB2A blocks:

| Field | Raw | Catalog conversion | Decoded |
| --- | ---: | --- | ---: |
| GWG32 max heating power | 29 | no conversion, % | 29 % |
| GWG62 boiler-controller gain | 30 | divide by 10 | 3.0 %/K |
| GWG63 boiler-controller reset time | 4 | multiply by 10 s | 40 s |
| GWG65 burner minimum pause | 4 | no conversion, min | 4 min |
| GWG71 burner minimum power | 29 | no conversion, % | 29 % |
| GWG72 modulating-burner offset | 20 | no conversion, K | 20 K |
| GWG73 modulating-burner startup optimization | 24 | multiply by 10 s | 240 s |
| GWG75 minimum internal-pump speed | 50 | no conversion, % | 50 % |
| GWG76 internal-pump overrun | 60 | no conversion, s | 60 s |

The important correction is GWG73:

```text
raw 24 * 10 s = 240 s = 4 min
```

Therefore GWG73 does **not** explain the measured approximately 12-second
post-flame regulation hold. The earlier 0.5 s/LSB hypothesis is rejected.

This also matches the broader Viessmann distinction between:

- startup optimization duration,
- regulation delay from ignition to beginning of control,
- burner-start delay,

which are separate concepts in other Vitotronic controller generations.

## Heating-power floor/ceiling convergence

The same catalog identifies:

```text
GWG32 = Begrenzung max. Heizleistung = 29 %
GWG71 = Brennerminimalleistung       = 29 %
```

On this coding plug those two limits are identical.

The measured burner characteristic additionally gives:

```text
30 % power -> modulation degree 33
```

and the live burner settles at:

```text
0x55DC ~= 33 %
A38F value ~= 31.5..33 %
```

after the startup ramp.

This creates a coherent picture:

1. the burner starts temporarily around modulation degree 65-66;
2. the controller holds that startup level for about 12 s;
3. the command then ramps downward at about 1 modulation percentage point/s;
4. the final heating operating point is forced to approximately the burner
   minimum because both the configured maximum heating-power field and burner
   minimum-power field are 29 %;
5. the burner characteristic maps that approximately 30 % power point to
   modulation degree 33.

This is strong evidence for why the observed steady heating modulation is
33 on this exact coding plug.

It does **not** by itself identify the hidden approximately 12-second
regulation-delay constant or the parameter controlling the 1 %/s command ramp.
