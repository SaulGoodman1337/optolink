- FF is present in the receive log, not just generated by JSON conversion or used by our code as a substitute for a timeout.
- The request addresses and one-byte lengths match the known source-defined reads. No accidental different read address is visible at these three points.
- A following P80=20 is not a checksum or general validity proof for the preceding runtime byte.
- These three FFs do not establish an actual 7650-rpm event, a real phase 255, a changed burner-controller identity or a fixed five-minute session lifetime.
- The origin of FF remains unresolved: device-side forwarding/unavailability and transport corruption are hypotheses, not established diagnoses. A host-side receive log is not an oscilloscope or an authenticated payload.

### Unchanged controls

The explicit execution still requires the configured CP2102 port, normal P300 settings, no Vitoconnect forwarding adapter and a running splitter. It remembers service states, pauses the running party emulator and splitter, obtains the same exclusive serial ownership, and confirms 20C2 plus the GFA branch before runtime reads. The original P300 restoration and restart policy remains in place.

Only the already used transmissions are enabled: EOT, VS2 initialization, ACK, Virtual_READ 00F8/2, independent P80, and same-session one-byte GFA reads at P06/P09/P10/P84/P80. There are no parameter, GFA, process, EEPROM or coding writes. No new register, arbitrary block read, burner command or keepalive is introduced. Serial pacing is not deliberately changed in this experiment; it is not a claim that rate limiting has fixed FF.

### New quality and recovery policy

1. **An FF on any of these five channels immediately quarantines the entire current round.** Raw bytes and timestamps are retained as a `rejected_round`, but `decoded` is null. FF is not multiplied into RPM, converted to a phase change, replaced with zero or replaced with the last good value.
2. **The active session is no longer trusted after that round.** There is no immediate bare reread or accepting FF as identity. The first new protocol operation is EOT, followed by a complete P300 identity check.
3. A new segment requires P300 00F8/2=20C2, **two independently synchronized P80=20 reads**, and another same-session P80=20 check. Only then can runtime sampling resume. Every re-identification is recorded with its gap and segment number.
4. At most **three** such sequences are attempted per execution. A further FF before ten accepted rounds after re-entry is fatal rather than producing a retry loop. FF during re-identification, an incorrect non-FF P80, timeout, queued/trailing data, partial write or another transport failure is fatal.
5. Recovery has a cooperative 20-second budget, bounded also by the original observation deadline; it is not started with less than 15 seconds left. The observation clock is not restarted after a gap. No new round starts after the original observation window.
6. Phase comparisons are reset across gaps. The script never invents a phase transition through missing data. Accepted-round and attempted-round numbering are separate.
7. The actual observation end/failure elapsed time and the last accepted-round elapsed time are now separate summary fields. The stale elapsed-time issue of the original logger is not carried forward.

This is deliberately conservative **sample-quality policy**, not proof that FF is universally invalid in the entire GFA protocol. On a scaled channel FF could in principle be a legitimate endpoint value; this diagnostic chooses to withhold it pending clarification. Other non-FF corruption is not ruled out by the policy either. Records therefore say `accepted_by_policy_not_independently_verified`, not physically validated.

### Results are not silently upgraded after recovery

| Result | Exit code | Meaning |
| --- | ---: | --- |
| `PASS` | 0 | Requested observation completed without rejected rounds; closing identity and P300/services verified by the helper. |
| `COMPLETE_WITH_GAPS` | 2 | Window completed and communication/services restored, but one or more rounds were quarantined and new segments were opened. Not an uninterrupted successful session. |
| `FAIL` | 1 | Acquisition, re-identification or final restoration did not meet the criteria. Inspect the log before retrying. |

None of these statuses proves a complete burner cycle, physical fan calibration, the precise flame-establishment time or renewed Home Assistant freshness. The helper still does not poll flame, pump, temperatures, 55DC or 55E0.

## 3. Offline verification actually performed

The exact committed file passed compilation, plan-only execution, and **109 offline tests**: 23 P80 tests, 33 session tests, 33 original cycle tests and 20 new quality-policy tests. The new tests cover FF at each runtime channel and P80, preservation of raw rejected records, no FF-derived RPM/phase output, EOT/P300-before-resume order, repeated/early FF, the three-reconnection cap, wrong identity, tail bytes, failure during re-identification, time budgets, disk failure, interruption, gap-free versus gap-completed status, and separation of failure time from last accepted time.

The tests use fake serial/systemd objects and simulated time. Earlier original tests also ran against the new lifecycle during development; no actual serial device was opened by these checks. Offline success is not hardware evidence that FF will disappear or that the new re-entry sequence will succeed on an appliance after an anomaly.

pyserial API behavior was checked against its official reference: https://pyserial.readthedocs.io/en/latest/pyserial_api.html . A read returns received bytes or fewer bytes on timeout; our code does not synthesize FF for an empty read.

No full `update` or new collector run is needed. This diagnostic is not run automatically by an installer/updater. `COMPLETE_WITH_GAPS` intentionally returns exit code 2; that is not a Python crash or a reason to rerun immediately.

Supply both files after the run; the existing raw excerpts and old JSONL need not be resent. Check actual HA data refresh separately after service recovery.

Ordinary SIGINT/SIGTERM/SIGHUP enter cleanup. There is no independent watchdog or absolute recovery guarantee for SIGKILL, power loss, disconnected USB, kernel stalls or failed service jobs. The original P80 runbook's manual recovery procedure still applies after the helper has exited.

## 5. Remaining research

If re-identification succeeds, preserve the gaps and compare error counts/operating states. This is resilient diagnostic acquisition, not a root-cause finding. If no FF occurs, that run alone does not prove the fault fixed. If FF persists, re-identification fails or another framing error appears, inspect that new raw trace rather than broadening the command set.

Possible later work includes source-backed validity/sentinel semantics, controlled pacing comparisons or physical-link analysis. Those are distinct experiments. Firmware readout/update, E7 persistence, pump control, coding-plug changes and permanent HA integration remain separate and are not solved by this patch. Production profiles, dashboard YAML, heating codings and firmware were not changed.
