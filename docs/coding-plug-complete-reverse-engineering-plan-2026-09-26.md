# WB2A coding-plug complete reverse-engineering and image-generation plan - 2026-09-26

## Purpose

This document defines the long-term research target for the Viessmann WB2A /
VDensHO1 / 20C2 coding plug.

The target is **not** merely to clone an existing plug or to patch one known
byte. The target is to understand both physical EEPROM images sufficiently
well that every generated byte is either:

1. semantically understood and intentionally generated;
2. structurally/integrity-derived by a reproduced algorithm; or
3. explicitly classified as an invariant/opaque byte that must be inherited
   from a proven-compatible reference image.

Only after that standard is met should the project consider producing custom
coding-plug images for bench validation.

This work is related to, but distinct from:

- #36 - physical f01/f02 EEPROM capture and software correlation;
- #25 - local regulation-board MCU identification and firmware readout.

## Safety and scope

The coding plug carries controller-, boiler-, pump- and burner-related
configuration. Incorrect images may be rejected by the controller or may alter
operating limits.

Therefore:

- production hardware remains read-only by default;
- no unknown byte is treated as a safe write target;
- no generated image is written to the installed production plug;
- image generation is an offline research capability first;
- any later write test must use spare/replaceable hardware where possible;
- raw MCU firmware remains private if obtained; public repository material
  should contain hashes, derived structure and reproducible analysis rather
  than proprietary firmware blobs;
- MCU unlock/erase operations are out of scope.

## Physical architecture established so far

The coding-plug PCB contains two separate 4-Kbit / 512-byte I2C EEPROMs.

### f01 / SIM1

- STMicroelectronics 24C04-class device;
- 512-byte physical image;
- proven to contain the main regulation / GWG / P300 coding-plug dataset.

For the verified range:

```text
P300 address = 0x1000 + physical f01 EEPROM offset
```

The active 7833971 dump is byte-correlated against the live P300 coding-plug
view.

### f02 / SIM2

- Microchip 24LC04B-class device;
- 512-byte physical image;
- proven to contain a GFA / fire-control coding-plug dataset;
- P101..P106 have direct same-plug physical-to-live mapping at offsets
  0x0E..0x13.

The two EEPROMs must therefore be treated as separate coding domains with
different validation and consumer behavior.

## f01 state: regulation / GWG side

### Proven mapping

The active image confirms the physical-to-P300 relation throughout the
verified coding-plug blocks.

Examples:

```text
f01 0x10 -> P300 0x1010 -> ASCII part number
f01 0x20 -> P300 0x1020
f01 0x30 -> P300 0x1030
f01 0x40 -> P300 0x1040
...
```

Decoded/source-backed parameters include, among others:

- GWG30 - DHW power limit;
- GWG32 - heating power limit;
- GWG34 - diverter-valve configuration;
- GWG5A - maximum DHW setpoint;
- GWG5C / GWG5D - absolute DHW/heating power limits;
- GWG60..67 - boiler regulator constants;
- GWG70 - minimum boiler temperature;
- GWG71 - burner minimum power;
- GWG72 - modulating-burner offset;
- GWG73 - startup optimization;
- GWG74 - storage-mode boiler target power;
- GWG75 - minimum internal-pump speed;
- GWG76 - internal-pump overrun;
- GWG80..88 - DHW/DLH regulator fields;
- GWG91..9A - burner characteristic fields;
- GWGC0..CA - Grundfos diverter motion profile.

### Differential evidence

The 7823363 -> 7833968 f01 comparison is highly constrained:

- 499/512 bytes are identical;
- only 13 bytes differ.

Important semantic deltas include:

```text
GWG30 70 -> 85 %
GWG32 70 -> 60 %
GWG5A 60 -> 63 C
GWG74 70 -> 100 %
GWG75 100 -> 50 %
```

The pump-related physical relation is directly visible:

```text
7823363 f01[0x75] = 0x64 = 100 %
7833968 f01[0x75] = 0x32 =  50 %
7833971 f01[0x75] = 0x32 =  50 %
```

### f01 integrity gap

Two additional bytes change in the 7823363 -> 7833968 comparison:

```text
0x00E 52 -> D4
0x00F E6 -> 6C
```

They are plausible integrity/check bytes, but no checksum/CRC algorithm or
coverage range is yet proven.

Until those bytes are explained, a fully synthetic f01 generator is not
considered complete.

A template-based patcher could preserve them, but that is a weaker capability
than understanding and regenerating them correctly.

## f02 state: GFA / fire-control side

### Proven direct mapping

For active 7833971:

```text
physical f02[0x0E] = P101 = 15
physical f02[0x0F] = P102 = 01
physical f02[0x10] = P103 = 14
physical f02[0x11] = P104 = 0C
physical f02[0x12] = P105 = 04
physical f02[0x13] = P106 = D6
```

This is same-plug hardware-to-live GFA correlation.

P103/P104/P105 are source-labelled day/month/year fields. Their display
encoding remains intentionally unresolved.

P106 is source-labelled as a CRC-related diagnostic byte. Its algorithm,
coverage, seed and transformation remain unknown.

### Remaining unmapped live fields

The active GFA view also exposes:

```text
P90  = 00
P100 = 63
P107 = 02
P108 = 00
```

No unique physical offsets are yet assigned.

P100 illustrates the ambiguity particularly well. The raw value 0x63 occurs at:

```text
0x02B
0x046
0x07D
0x098
```

The pairs align with the repeated internal record structure, so a single-byte
match cannot identify the semantic field.

### f02 record/redundancy structure

A long record-like sequence begins at approximately 0x14 and repeats at 0x66.

```text
record start A = 0x14
record start B = 0x66
distance       = 82 bytes
```

At least 71 bytes are duplicated between the two regions in the known images.

This is consistent with, but does not yet prove:

- primary/backup records;
- two consumer copies;
- mirrored integrity storage;
- or another manufacturer-specific redundant layout.

Additional variable/control-like bytes occur in the tail region around
0xE2..0xEF and at 0x1FF. Their meaning is not yet established.

## Coding-plug identity relation now understood

The controller-side summary:

```text
0x7656 = 20 15 02 01
```

has been semantically resolved as:

```text
byte 0 = KS_Karte_GWG_Typ      = 20 = P80
byte 1 = KS_Karte_GWG_Kennung  = 15 = P101
byte 2 = KS_Karte_GWG_Rev_R    = 02 = P107
byte 3 = KS_Karte_GWG_Rev_F    = 01 = P102
```

Therefore the project notation `2015:0201` is an identity/revision tuple, not
a calendar date.

A second physical/software relation is:

```text
0x1040 = 02 15 ...
          |  |
          |  +-- P101
          +----- P107
```

This cross-links the regulation-side and GFA-side identity namespaces.

## Capability assessment

### A. Byte-identical cloning of a known plug

For a fully captured known plug such as active 7833971, both 512-byte images
exist. Creating byte-identical offline copies is therefore mechanically
possible.

This does **not** imply that arbitrary generated images are understood.

### B. Template-based modification of known f01 fields

Many f01 fields can already be changed at known physical offsets.

However, doing so without understanding 0x0E/0x0F risks producing an internally
inconsistent image.

The project should therefore distinguish:

- `patch existing image`;
- `rebuild image from semantic fields`;
- `generate image from scratch`.

These are separate maturity levels.

### C. Fully synthetic f01 generation

Not yet complete.

Minimum blocker:

- reproduce the f01 integrity/check algorithm and its byte coverage.

### D. Fully synthetic f02 generation

Not yet justified.

Minimum blockers:

- map P90;
- map P100;
- map P107;
- map P108;
- reproduce P106 CRC/integrity calculation;
- explain/validate the repeated record structure;
- understand tail/control bytes sufficiently to know what must be generated,
  mirrored, copied or incremented.

### E. Complete custom coding-plug image pair

Not yet justified.

The final goal requires both f01 and f02 to be independently validated and
cross-consistent.

## Proposed research phases

### Phase 1 - Preserve and normalize evidence

- keep all raw EEPROM dumps immutable;
- preserve SHA256 files;
- record physical side, part number, external label and capture provenance;
- prefer 3x independent reads for future captures;
- normalize all comparisons into machine-readable JSON.

### Phase 2 - Build an offline parser/validator

Before building a writer, implement a read-only tool such as:

`tools/wb2a-coding-plug.py`

Desired initial commands:

```text
inspect
diff
validate
decode-f01
decode-f02
```

It should:

- identify f01 vs f02;
- decode known semantic fields;
- display unresolved bytes/regions explicitly;
- validate known mirror/complement relations;
- compare image fields against known part/revision profiles;
- never silently accept unknown integrity state.

### Phase 3 - Solve f01 integrity bytes

Use all available f01 images to test candidate algorithms and ranges.

Candidate families should include, without assuming any one is correct:

- additive 8/16-bit checksums;
- one's/two's complement checks;
- Fletcher variants;
- common CRC-8 variants;
- common CRC-16 variants;
- byte-swapped CRC/check values;
- partial-range and multi-range coverage;
- exclusion/inclusion of the checksum bytes themselves.

A candidate is accepted only when it reproduces every known image and remains
consistent across newly captured variants.

### Phase 4 - Solve f02 mapping and integrity

Highest-value evidence is a plug whose GFA values differ from the current
three samples, especially:

- different P100;
- different P107/P108;
- different date/P106;
- different P90/type.

Differential evidence should be preferred over guessing from repeated byte
values.

For P106, systematically test CRC/checksum hypotheses against the complete f02
images and against plausible record-level subranges.

### Phase 5 - Determine record semantics

For the repeated 82-byte f02 structure determine:

- whether both copies are consumed;
- whether one is active and one backup;
- whether sequence/version markers exist;
- whether tail bytes select the active copy;
- whether checksums are per-record or global;
- whether 0x1FF is a marker, checksum, generation counter or unrelated value.

No image builder should rewrite/mirror these regions until this is known or a
safe invariant-preservation rule is proven.

## MCU firmware as an explicit research dependency

The local regulation MCU/firmware work in #25 may become the shortest path to
closing the remaining coding-plug questions.

A firmware dump is **not required before continuing offline EEPROM
differential analysis**. We can still:

- solve simple checksum/CRC candidates;
- map fields using multiple physical plug variants;
- build a parser/validator;
- document invariants and unknown ranges.

However, firmware should become the preferred next source when offline
evidence stops being discriminative.

Firmware analysis could directly reveal:

- f01 checksum/CRC routine and coverage;
- f02 CRC/P106 algorithm;
- dual-record validation logic;
- active/backup record selection;
- default/fallback behavior;
- cross-checks between f01, f02 and controller identity;
- range validation and parameter clamps;
- whether some bytes are transformed/synthesized rather than copied;
- rejection/fault paths for invalid coding plugs.

Therefore the recommended strategy is:

1. continue non-invasive offline analysis now;
2. do **not** force ambiguous field assignments merely to finish a generator;
3. wait for the MCU firmware path once checksum/mirror questions become
   underdetermined by available EEPROM samples;
4. use firmware findings to verify rather than merely speculate about image
   generation rules.

## Generator maturity model

### Level 0 - archive/clone

- read and hash both EEPROM images;
- byte-identical duplication only.

### Level 1 - semantic inspector

- decode known f01/f02 fields;
- no mutation.

### Level 2 - template patcher

- patch explicitly known fields in a compatible reference image;
- preserve unresolved bytes;
- recalculate only proven integrity fields.

### Level 3 - deterministic rebuilder

- regenerate all variable bytes in both images from a structured semantic
  profile;
- reproduce all integrity, mirror and identity relationships;
- round-trip known images.

### Level 4 - custom profile generator

- generate a new compatible f01/f02 pair from selected supported semantic
  parameters;
- validate all cross-domain constraints;
- reject combinations not proven safe/valid.

The project is currently between Level 1 and Level 2. It is not yet at Level 3.

## Acceptance criteria for a complete image generator

The project should not claim "complete generator" until all of the following
are true:

- [ ] every known variable f01 byte has a semantic or integrity explanation;
- [ ] f01 0x0E/0x0F algorithm and coverage reproduced;
- [ ] f02 P90 physical mapping resolved;
- [ ] f02 P100 physical mapping resolved;
- [ ] f02 P107 physical mapping resolved;
- [ ] f02 P108 physical mapping resolved;
- [ ] P106 CRC/integrity algorithm reproduced;
- [ ] repeated f02 record semantics understood or safely reproduced by a
      proven rule;
- [ ] tail/control region semantics or invariant-preservation requirements
      established;
- [ ] cross-consistency rules between f01, f02, 0x7656 and GFA identity are
      implemented;
- [ ] parser validates all archived known-good images;
- [ ] rebuild -> binary comparison succeeds for known profiles, except for
      explicitly documented non-deterministic bytes;
- [ ] mutation tests prove that intended semantic changes produce only the
      expected derived byte changes;
- [ ] malformed combinations are rejected by the offline validator;
- [ ] first hardware tests use spare hardware with verified backup/restore
      procedure;
- [ ] no production-plug write is required to establish generator correctness.

## Current conclusion

The coding plug is no longer an opaque device.

The regulation-side f01 layout is already strongly understood and the
GFA-side f02 domain is physically proven, including a direct P101..P106
mapping. What prevents a scientifically defensible custom image generator is
primarily integrity/validation logic and a small number of unresolved f02
fields.

The project should continue with offline differential analysis, but should be
willing to pause at the point where the remaining questions become
underdetermined. At that point, the local MCU firmware from #25 is likely to
provide higher-value evidence than additional speculative EEPROM probing.
